# 批量条目工作流 / Batch Item Workflows

[中文](#中文) · [English](#english) · [返回工作流 / Back to workflows](workflows.md)

## 中文

这组命令减少 Codex 与 Zotero 之间的往返，不改变文献判断规则。它只使用 Zotero 官方 Local API，不需要新的 Bridge 路由、后台服务或持久缓存。

### 一次读取用于匹配的字段

```powershell
python scripts/zontex.py inventory --all
python scripts/zontex.py inventory --collection-name "Literature Review"
python scripts/zontex.py inventory --item-key ABCD2345 --item-key EFGH6789 --expect-count 2
```

`inventory` 自动翻页，只返回 key、version、item type、标题、首位作者、年份、现有 DOI / PMID / ISBN 与 collection key。它不返回完整 creators、标签、`Extra`、笔记正文或附件内容，因此适合让 agent 一次建立临时匹配表。

候选有可靠唯一标识时，直接与 inventory 中同类标识精确匹配，不要求用另一个数据库复核。没有标识时再比较规范化标题、首位作者和年份。语义冲突仍交给 agent 或用户决定；CLI 不维护隐藏索引。

### 一次创建多条文献

`create-items` 接受 JSON 数组，也接受带 `items` 的对象。推荐给每条记录一个只用于结果映射的 `clientId`：

```json
{
  "schemaVersion": 1,
  "items": [
    {
      "clientId": "citation-1",
      "itemType": "journalArticle",
      "title": "A Reproducible Benchmark",
      "creators": [
        {
          "creatorType": "author",
          "firstName": "Ada",
          "lastName": "Lovelace"
        }
      ],
      "date": "2026",
      "DOI": "10.1000/example",
      "collections": ["ABCD2345"],
      "tags": [
        {"tag": "/To Read"},
        {"tag": "Role/Method"},
        {"tag": "#Topic/Benchmarking"}
      ],
      "extra": "rate: 4"
    }
  ]
}
```

先预览结构和精确数量：

```powershell
python scripts/zontex.py create-items --json-file .\items.json --expect-count 35
```

用户确认整批后写入：

```powershell
python scripts/zontex.py create-items --json-file .\items.json --expect-count 35 --yes
```

命令会在首个 POST 前验证 manifest 的基本结构、`clientId`、`itemType` 和目标 collection。`key` 与 `version` 只能由 Zotero 生成，不能放入创建 payload。Zotero Local API 没有提供 item-template 端点，因此更深的字段合法性仍以官方 POST 响应为准。

已经决定的 collection、标签和 `Extra` 应直接放进创建 payload，避免创建后立刻再做一次相同 metadata 更新。CLI 内部按最多 50 条分批，并将 Zotero 的 successful / unchanged / failed 映射回 `clientId`。成功路径只做一次逻辑回读，默认输出计数、失败信息和必要 key，不回显完整 payload 或 Zotero 对象。

若某批出现失败或通信结果不确定，Zontex 停止后续批次，报告已创建、失败与未尝试的 `clientId`，不自动重放或删除已经创建的条目。修正失败项后，应把剩余项作为一批新的、再次确认的输入。

### API 往返变化

以 35 条全新文献为例，去重决策完成后的本地落库阶段可从大量逐条命令缩为：

| 阶段 | 逻辑调用 |
| --- | ---: |
| 全库 inventory | 每 100 条一页 |
| 创建 35 条 | 1 个批次 |
| 创建后回读 | 1 个批次 |

这不会消除外部检索、PDF 解析或模型语义判断的时间，但会明显减少 CLI 启动、Local API 往返和模型上下文中的重复 JSON。

## English

These commands reduce round trips between Codex and Zotero without changing literature judgment. They use only Zotero's official Local API and require no new Bridge route, background service, or persistent cache.

### Read matching fields once

```powershell
python scripts/zontex.py inventory --all
python scripts/zontex.py inventory --collection-name "Literature Review"
python scripts/zontex.py inventory --item-key ABCD2345 --item-key EFGH6789 --expect-count 2
```

`inventory` follows every page and returns only key, version, item type, title, first author, year, available DOI / PMID / ISBN values, and collection keys. It omits complete creators, tags, `Extra`, note bodies, and attachment content, so an agent can build one temporary matching table without carrying full Zotero objects through the conversation.

When a candidate has a reliable unique identifier, match it exactly against the same identifier type in the inventory without requiring another database to corroborate it. Without an identifier, compare normalized title, first author, and year. The agent or user still resolves semantic conflicts; the CLI keeps no hidden index.

### Create many papers once

`create-items` accepts either a JSON array or an object containing `items`. A per-record `clientId` is recommended solely for mapping results:

```json
{
  "schemaVersion": 1,
  "items": [
    {
      "clientId": "citation-1",
      "itemType": "journalArticle",
      "title": "A Reproducible Benchmark",
      "creators": [
        {
          "creatorType": "author",
          "firstName": "Ada",
          "lastName": "Lovelace"
        }
      ],
      "date": "2026",
      "DOI": "10.1000/example",
      "collections": ["ABCD2345"],
      "tags": [
        {"tag": "/To Read"},
        {"tag": "Role/Method"},
        {"tag": "#Topic/Benchmarking"}
      ],
      "extra": "rate: 4"
    }
  ]
}
```

Preview structure and the exact count first:

```powershell
python scripts/zontex.py create-items --json-file .\items.json --expect-count 35
```

After the user confirms the complete batch, write it:

```powershell
python scripts/zontex.py create-items --json-file .\items.json --expect-count 35 --yes
```

Before the first POST, the command validates the manifest's basic structure, `clientId` values, `itemType`, and target collections. `key` and `version` must be generated by Zotero and cannot appear in a create payload. Zotero Local API exposes no item-template endpoint, so deeper field validity remains governed by the official POST response.

Put already-decided collection membership, tags, and `Extra` directly in the create payload rather than immediately issuing a second metadata update. The CLI splits the input into batches of at most 50 and maps Zotero's successful / unchanged / failed groups back to `clientId`. The success path performs one logical readback. Default output contains counts, failures, and necessary keys rather than the complete payload or full Zotero objects.

If a batch fails or its transport outcome is uncertain, Zontex stops before later batches and reports created, failed, and not-attempted `clientId` values. It neither replays the input nor deletes items that were already created. Corrected or remaining records become a new batch that receives a new consolidated confirmation.

### API round trips

For 35 genuinely new papers, after deduplication decisions are complete, the local write stage becomes:

| Stage | Logical calls |
| --- | ---: |
| Complete library inventory | One page per 100 items |
| Create 35 items | One batch |
| Post-create readback | One batch |

This does not remove time spent on external retrieval, PDF parsing, or semantic model judgments. It does remove many CLI startups, Local API round trips, and repeated full-object JSON from the model context.
